# Step 04 — PostgreSQL schema and initialization

**Source:** [infra/schema.sql](../infra/schema.sql), [scripts/init_db.py](../scripts/init_db.py); commits [8848cfd](https://github.com/jarharsh1/Enterprise-QA-module/commit/8848cfda80178657a54bb974948c723d004636f9) and [b2d6a86](https://github.com/jarharsh1/Enterprise-QA-module/commit/b2d6a86b17e94adcd64313b5fef2b5d847a9fd3a).

## What we built and why

PostgreSQL holds relational metadata and state that should survive application restarts.

| Table | Purpose and implemented constraints |
| --- | --- |
| documents | UUID identifier, tenant, title, owner, allowed groups, globally unique S3 key, status restricted to pending/processing/ready/failed/retired, version and creation time |
| feedback | Actor, tenant, integer rating constrained to -1 through 1, note and timestamp |
| audit_events | Actor, tenant, action, JSONB details and timestamp |
| approvals | UUID generated by default, tenant, requester, question, pending default status, optional reviewer and review time |
| chat_messages | Tenant, conversation UUID, role constrained to user/assistant, content, timestamp |

Indexes: documents_acl_idx on tenant/status; audit_tenant_time on tenant/time descending; approvals_tenant_idx on tenant/status; chat_messages_session_idx on tenant/conversation/id descending. These support likely access patterns; they do not by themselves enforce authorization.

## Initialization

The script currently describes Render PostgreSQL. The dotenv template mentions RDS and the schema comment mentions Aurora. The implementation uses standard psycopg and DATABASE_URL rather than a provider-specific driver, so hosting should be confirmed separately.

From the repository root with a configured local .env:

```bash
python scripts/init_db.py
```

The script locates the project root using Path(__file__), loads .env, checks DATABASE_URL and schema existence, connects with a 15-second connection timeout, executes the schema in a transaction, and checks required tables via to_regclass. It returns exit code 0 on success and 1 on error.

Expected success: a message confirming all five required tables. No live execution was performed during this review. Re-running CREATE TABLE/INDEX IF NOT EXISTS preserves existing rows but does not migrate existing column definitions.

## Independent read-only verification

```sql
SELECT table_name
FROM information_schema.tables
WHERE table_schema = 'public'
  AND table_name IN ('documents', 'feedback', 'audit_events',
                     'approvals', 'chat_messages')
ORDER BY table_name;
```

Expected: five rows. Use a compatible PostgreSQL version with gen_random_uuid() available. Use a disposable database for initial validation; avoid printing connection URLs or sensitive exception details.

## Not implemented by schema alone

Row-level security, tenant authorization, full approval status-transition validation, version migrations, retention and encryption policies remain application/infrastructure concerns. The existence of a table does not mean the associated feature is working.
